# hashlib optimization loops — 2026-04-24 follow-up session

This session continues the codex-driven loop strategy on `kernel/hashlib.h`.
Loops 1–5 were the prior codex session (baseline → 1.151× geomean).
Loops 6–10 below were added in this session on top of loop 5.

**Correctness fix:** A follow-up commit (`7ab7606ff`) repaired loop 10's
fastmod by also propagating the precomputed magic through `swap()` and
`clear()`. The original loop 10 commit was caught by `tests/various`
(`wreduce.ys`, `wreduce2.ys`, `peepopt.ys`, `muxpack.ys` regressed) —
swapped dicts were silently using each other's magic, mapping lookups
to wrong buckets. After the fix every yosys test suite that runs in our
build configuration matches the loop-5 baseline bit-for-bit. The
performance numbers below are for the fixed loop 10 — the original
buggy version reported a misleading 1.38× on `wide_opt_chain_3000`
because broken bucket lookups silently dropped repeat operations.

All numbers are wall-clock medians from `tests/tools/benchmark_yosys.py`,
5 measured runs (default cases) / 3 measured runs (synthetic cases) with
1 warmup each. Microbench numbers are medians over 5 runs of
`benchmark-results/hashlib_microbench.exe`.

## Per-loop change summary

| # | Change | Status | Notes |
|---|---|---|---|
| 6 | Cache `entries.data()` + `hashtable.data()` in `do_rehash` and `do_erase` | ✅ accepted (`cd5b1d025`) | Compiler couldn't prove the data pointers were loop-invariant across opaque `do_hash`/`ops.cmp` calls. ~+7% geomean on top of loop 5. |
| 7a | Lemire multiply-shift bucket compression in `do_hash` | ❌ rejected | Microbench gained ~1.17×, but the new bucket *assignment* changed iteration order, which exposed an order-fragile fixed-point loop in yosys' `opt` pass — `opt -fast` after `synth -noabc` ran 600k+ iterations without converging. |
| 7b | `udata_hash` field cached in `entry_t` (skip recompute in `do_rehash`/erase back-fill) | ❌ rejected | +4 bytes per entry hurt cache more than the rehash savings helped. ~1% geomean regression. Also caused intermittent `pool<> assert failed` from default-constructor leaving `udata_hash` uninitialized. |
| 7c | Inline `do_hash` in `do_rehash` and `do_erase` to skip the `!hashtable.empty()` branch | ❌ rejected | ~2% geomean regression — the empty check is already well-predicted, the speculative inlining cost more than it saved. |
| 7 | Disable hashlib runtime asserts unless `YOSYS_HASHLIB_DEBUG` is set | ✅ accepted (`41bf34dfa`) | The original code only gated assertions on `NDEBUG`, which yosys does not define for release builds. Every chain walk and rehash was paying for a runtime branch + bounds check. ~+2-3% on dict/pool microbench. |
| 8 | Software-prefetch `entries[i+8]` while processing `entries[i]` in `do_rehash` | ✅ accepted (`d9f51d71a`) | The longest hot loop in hashlib is bound by L2/L3 latency for large tables. ~+1% net synth-suite, biggest single-case gain on `opt_share` (1.06× vs prior). |
| 9a | Speculative-load `entries[index].next` *before* `ops.cmp` in chain walks | ❌ rejected | -35% on dict_lookup microbench — the typical chain length at load factor 0.5 is 0–1, so the speculative load was pure overhead in the common case. |
| 9 | Prefetch the next chain entry only *after* `ops.cmp` decides to advance | ✅ accepted (`06ab89826`) | -8% dict_lookup, -13% pool_count, -4% pool_insert/erase on microbench. Synth-suite within noise (chains are short). |
| 10 | Replace runtime `% size` with libdivide-style fastmod (Lemire reciprocal) | ✅ accepted (`5cba01847`, fixed in `7ab7606ff`) | 32-bit divmod against a runtime divisor is ~25-40 cycles; fastmod is two 64×64→128 multiplies. Bucket assignment is bit-exact with the prior `% size` (verified against ground-truth `%` for every prime in `hashtable_size()`'s table). Initial commit silently broke `swap()` and `clear()`; fix in `7ab7606ff` propagates the precomputed magic through both. Real (post-fix) gain: ~+8% geomean over loop 5. |

The codex session reported 1.151× geomean baseline → loop 5. This session
added another ~1.05× on top, bringing total to ~1.21× over the original
baseline.

The earlier reported 1.28× and the 1.443× for `wide_opt_chain_3000`
were partly artifacts of the loop-10 swap/clear bug — broken bucket
lookups in some passes silently dropped repeat hash operations, making
those passes appear faster than they were. The post-fix numbers are
the ones to trust.

## What worked, what didn't, why

**Worked:**
- Caching `vector::data()` to defeat aliasing (loop 6).
- Removing dead asserts that the build wasn't compiling out (loop 7).
- Targeted prefetching on actually-long memory dependencies (loops 8, 9).
- libdivide-style fastmod — preserves bucket assignment, slashes the
  per-operation cycle count (loop 10).

**Didn't work:**
- Anything that changed iteration order (Lemire-as-bucket, power-of-two
  sizing). The yosys opt passes are not robust to permutation of
  hash-table iteration order, even when chain semantics are preserved.
  Likely a real latent bug in yosys, but out of scope here.
- Storing extra state per entry. The +4-byte `udata_hash` field hurt
  cache density more than the saved hash recomputation helped, even on
  large tables.
- Speculatively loading the next chain entry — load-factor 0.5 means
  most chains have ≤1 element, so the speculative load is pure waste.

## Where the next ~1.5×–2× would have to come from

The cheap, safe wins are now mostly harvested. Larger gains require
touching things this session deliberately avoided:

1. **Hash quality + power-of-two sizing.** DJB32 has known clustering on
   yosys' SigBit/IdString patterns; replacing the finalizer with FxHash
   or wyhash and switching to power-of-two sizes would let bucket
   compression collapse to a single `&` instead of fastmod. Blocked on
   the order-fragility issue from loop 7a — the hash mixing has to
   improve *at the same time* as bucket placement changes, otherwise
   the order-sensitive opt code regresses.
2. **Open addressing / Robin Hood / SwissTable.** Removes the chain
   indirection entirely. Major rewrite, also changes iteration order.
3. **Inline hash tag in `entry_t`.** Loop 7b approach revisited with a
   1-byte tag that fits in existing struct padding for common K/T
   sizes. Would let chain walks fast-reject before `ops.cmp`.

## Reproducing

```
benchmark-results/run_loop.sh <label>
```

Builds the microbench, rebuilds yosys.exe (with a response-file link
to work around Windows command-line length limits), runs the default
case suite (`simple_synth_noabc`, `opt_share_large_pmux_cat`) and the
synthetic case suite (`many_equiv_cells_*`, `wide_opt_chain_3000`),
and writes JSON summaries + per-run logs to `benchmark-results/`.

The run_loop.sh script also force-rebuilds any `.o` files older than
`kernel/hashlib.h` — needed because the existing yosys Makefile's
parallel-make path occasionally skips subdirectory recompiles after a
hashlib.h touch, leaving stale `.o` files with the wrong `entry_t`
layout. (This caused several spurious `pool<> assert failed` runtime
failures during this session before the workaround landed.)
